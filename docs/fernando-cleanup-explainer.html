02 · WHAT CHANGED

Six practical improvements

TL;DR
Each change reduces a specific kind of risk: confusion, privacy mistakes, accidental deletion, duplicated rules, oversized files, or silent regressions.
Remove

Dead AI-provider code

Unused Ollama, Gemini, and OpenRouter paths were removed from main_api.py. Hermes now has fewer misleading branches around the supported provider choices.

Protect

Private local files

Legacy natal-chart and board files were added to .gitignore. This reduces the chance that personal data is added to Git again.

Guard

Safe cleanup preview

A dry-run tool reports only approved generated folders. It has no delete mode and explicitly protects editorial knowledge and private data.

Centralize

Board and diary operations

Repeated create, update, and field-handling rules moved into typed utilities. Screens now call one shared rule instead of rebuilding it in several places.

Separate

Large UI responsibilities

Board management moved out of MesaCriacao, and Mandala orientation math moved out of its visual component. Each file now has a narrower job.

Verify

Tests, types, and lint fixes

New tests cover owner isolation, diary fields, board operations, Mandala geometry, active subjects, and archive behavior. A direct frontend type-check command was also added.

03 · STRUCTURE

One rule, one clear home

TL;DR
The main structural benefit is not visual. Business rules and calculations now live outside screen components, where they are easier to test and reuse.

Before

  • Large components mixed display and data rules.
  • Similar operations were repeated in different screens.
  • Geometry was coupled to rendering code.

After

  • BoardManager owns board management.
  • board.ts and diary.ts hold shared typed operations.
  • mandalaGeometry.ts holds testable orientation logic.
Why this helps future development
A future change has fewer places to inspect. A correction to a shared operation can be tested without opening the full screen. Smaller components also reduce the chance that an unrelated visual change breaks data behavior.
04 · SAFETY

Cleanup with boundaries

TL;DR
The branch treats cleanup as a controlled report-and-test process. It does not add a broad deletion command.
Allowed to report

Generated output only

dist/, build/, Rust build output, selected Python caches, and one known error file are on a fixed allowlist.

Explicitly protected

Knowledge and personal data

The tool does not target node_modules, environments, worktrees, private data, or the editorial astrology database.

What “dry run” means
The command python tools/dry_run_cleanup.py only prints what a future cleanup could consider. It cannot remove, move, or overwrite a file. Any destructive cleanup still needs separate review and explicit approval.
05 · EVIDENCE

The important behavior now has alarms

TL;DR
Automated tests act like alarms. They do not prove that all future changes are safe, but they catch several known failure types earlier.
✓
Private owner isolation
Tests check that one owner cannot read or change another owner’s private records.
✓
Diary field preservation
Tests check optional and omitted fields so an update does not silently erase information.
✓
Active subject fallback
Tests check that the application selects and persists a valid subject when the current selection is no longer valid.
✓
Pure geometry and board rules
Small utility tests check Mandala orientation and board operations without depending on a full page render.
✓
Static checks
npm run typecheck gives contributors a direct way to find TypeScript errors; audited ESLint errors were also corrected.

06 · LIMITS

What this work does not claim

TL;DR
This branch improves maintainability and safeguards. It does not by itself certify the complete product or replace manual user acceptance.

Reasonable conclusions

  • The supported code path is clearer.
  • Several private-data boundaries have regression tests.
  • Repeated UI logic has clearer ownership.
  • Generated-file cleanup can be inspected safely.

Not claimed here

  • No claim that every project defect is fixed.
  • No claim that all local environments have identical dependencies.
  • No claim that the full Chrome workflow was manually accepted.
  • No destructive cleanup was performed.
Bottom line: the project has a smaller maintenance surface and stronger guardrails. That makes later feature work less risky, but normal build, test, and human acceptance checks are still required.
